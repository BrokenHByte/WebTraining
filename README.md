# Учебный проект
Проект для практики навыков по созданию сервисов в фреймворке ASP.NET Core  
Проект разделён на 3 микросервиса:  
**Events - мероприятия**  
**Bookings - бронирование**  
**Authorization - авторизация**  

Каждый проект разделен на 4 слоя:  
**Domain** - ядро системы. Определены классы бизнес-сущностей  
**Application** - слой реализующий бизнес логику через сценарии взаимодействия пользователя с сервером  
**Infrastructure** - слой хранит реализации интерфейсов взаимодействия с базой данных и другими внешними системами. Миграции баз данных и конфигурации для бизнес-сущностей в базе  
**Presentation** - слой доступа к пользовательским сценариям через контроллеры  

Отдельное выделен проект **Core**, который объединяет контракты, топики и обёртки для сервисов Kafka.  
Проект подключается к проектам микросервиса как общий .csproj  

# Сборка и запуск
1. Клонировать репозиторий с необходимой веткой
2. Скопировать и переименовать файл **.env.example** в **.env**  
Заполнить конфигурацию внутри .env файла  
Установить пароли для базы данных и JWT_KEY
3. Запустить все проекты решения в docker,  
запустив из корня репозитория **docker compose up -d --build**  
(При появлении ошибки, убедитесь что docker установлен и сервис запущен)
4. Три микросервиса будут расположены по адресам:
`http://localhost:5001/swagger/index.html`
`http://localhost:5002/swagger/index.html`
`http://localhost:5003/swagger/index.html`

Для отладки рекомендуется использовать Multi-Launch настроеный в вашей среде разработки  
Для запуска выделить проекты  
**Authorization.Presentation.csproj**  
**Events.Presentation.csproj**  
**Bookings.Presentation.csproj**  
Отладка преполагает использование локальной базы Postgres, внутри неё создаются 3 базы данных  
В качестве базы данных используется postgres-16
  
# Кэширование  
Для кэширования отдельных запросов используется хранилище Redis  
Кэшируется api получения события по ключу (/events/{id}) и получение топ-10 событий с наибольшим процентом проданных мест (/events/top)  
Для топ-10 событий инвалидация происходит только по ttl, актуальность этих данных не слишком важна  
События получаемые по ключу, инвалидируются через удаление ключей, при любых действиях с событием (изменение, удаление, резервирование, освобождение мест)  
В случае недоступности redis, данные получаются напрямую из базы  
ttl для /events/{id} = 10 минут  
ttl для /events/top = 15 минут  

# Инструменты мониторинга
1. Prometheus - сбор метрик    
Можно проверить что метрики доступны по адресу /metrics, для любого сервиса  
Сам сервис расположен на порту 9090. Можно убедится в правильном подключении к сервисам по пути :9090/targets  
2. Jaeger - отслеживание трейсов  
UI сервиса доступно на порту 16686  
3. Grafana - визуализация данных мониторинга  
UI сервиса доступно на порту 3000  
Можно использовать файл metrics.json для создания дашборда с метриками:    
http_server_request_duration_seconds  
http_server_active_requests  
http_server_request_duration_seconds_count  
dotnet_thread_pool_queue_length_total  
dotnet_gc_collections_total  

# Аутентификация и авторизация  
1. Используя Swagger (http://localhost:5003/auth/register) создайте пользователя с правами "Admin" или "User"  
   (пользователи без прав администратора не могут управлять событиями и удалять чужие бронирования)
2. Авторизуйтесь в Swagger (http://localhost:5003/auth/login)  
3. Полученный в результате авторизации токен скопируйте в поле по кнопке "Authorize" в двух других микросервисах 
4. Проверка результата: токен должен передаваться в Header в любых запросах к серверу из Events и Bookings   

В случае проблем с авторизацией возвращает:  
401 - если никакой пользователь не авторизован  
403 - если прав пользователь не достаточно

# Доступное API

В качестве примера, localhost  

### Регистрация  
POST localhost:5003/auth/register  
**Тело запроса**
```json
{
  "login": "Ваш логин",
  "password": "Ваш пароль",
  "role": "Права" (Admin or User)
}
```  
**Возвращает**  
204 при успехе  
409 если указанный логин уже существует

### Бронирование
Порядок бронирования
1. Выбираем событие на основании **GET localhost:5001/events**
2. Бронируем событие через **POST localhost:5002/bookings/{id}/book**
3. Проверяем статус брони через **GET localhost:5002/bookings/{id}**

Бронирование изначально создаёт событие со статусом Pending  
и информирует микросервис Events о новой брони.  
Далее если Events подтверждает возможность брони и захватывает место, Bookings по соответствующему сообщению переводит бронь в состояние Confirmed


------------------------
### Забронировать событие по id 
POST localhost:5002/bookings/{id}/book (Достаточно прав пользователя)  

**Пример ответа:**
```json
{
  "id": "a75f87e4-de26-4a8c-93aa-9df9dd32a3b5",
  "eventId": "5decc173-b4be-4fc6-96f9-04c276290099",
  "status": "Pending"
}
```
**Возвращает**  
202 если бронь зарегистрирована  
404 если событие не найдено  
409 если мест для бронирования в событии не осталось 

------------------------ 
### Отмена бронирования по id брони  
DELETE localhost:5002/bookings/{id} (Достаточно прав пользователя)  
(Необходимы права администратора в случае отмены чужой брони)  
(Бронь не удаляется из базы, только отменяется)
**Возвращает**   
200 если бронь отменена  
404 если бронь не найдена    
403 если прав пользователя не достаточно  

------------------------
### Проверка статуса бронирования по id брони
GET localhost:5002/bookings/{id} (Достаточно прав пользователя)  

**Пример ответа:**

Возвращает полную модель бронирования
```json
{
  "id": "e1351cf3-ae1f-4882-8217-49a26e484b00",
  "eventId": "c4856d85-2955-4e1c-b173-134689f03916",
  "status": "Confirmed",
  "createdAt": "2026-05-25T06:45:49.5022756Z",
  "processedAt": "2026-05-25T06:45:51.5905483Z"
}
```
Варианты status:    
Pending, Confirmed, Rejected, Cancelled

**Возвращает**  
200 если успешно  
404 если бронирование не найдено
